## 2026-10-20 — Boundary decision [Governance]

The assistant works **clean-room documentation side only**: it does **not** open,
decompile, extract, or transcribe anything in `RESOURCES/`, and does not produce
specs claimed to be derived from the proprietary firmware. White papers are
sourced from **public interoperability references** (SwitchBrew, Atmosphère /
libstratosphere, LibHac, hactool/nstool). Firmware-specific values that need
confirmation are recorded as Verification-Ledger open items, never guessed or
laundered from research material. This keeps every white paper's provenance clean
(Rule 0, Rule W). Recorded so later contributors know these papers' sourcing.

## 2026-10-20 — Slice S002 · Research tooling methodology [Governance/Research]

**Plan IDs:** PR.2, PR.3, PR.4, PR.5, P2.5
**Artifact:** `docs/research-tooling.md`

Codifies the appropriate division of labor for automating decompilation/analysis:
tooling extracts **interface-level facts** (command IDs, payload layouts, boundary
behavior) that a researcher reviews and authors into white papers; it does not
reconstruct internal algorithms or transcribe function bodies. Defines a 5-stage
pipeline (catalog/format parse → static interface extraction → dynamic IPC
observation → version diff → review), maps each stage to the three stated targets
(API surface + command IDs; IPC payload layouts; sync/handles/error mappings), and
lists a tool inventory with build status. All tool output stays in `RESOURCES/`;
only authored white papers leave (Rule C).

Boundary (recorded): assistance covers building the extractors/analyzers and the
methodology; it excludes transcribing decompiled bodies and building function-body
exporters for transcription.

### Next (tooling)
- Pick first tool to implement. Recommended: **Radar** on-device IPC tracer +
  host trace analyzer (Stage C) — black-box, cleanest provenance, yields all three
  targets as observed facts. Natural second: static dispatch-table extractor
  (Stage B) for the static↔dynamic cross-check.
